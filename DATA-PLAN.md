- `経路をいくつか登録できて、1つを選択する。その経路上の位置情報と乗り換え情報からどの電車に乗れそうか表示する。例えば今いる場所から歩いて10分で次の駅に着くならダイヤから10分後の電車を提案する。さらに個人の歩く道とスピードを学習してより正確な案内をしたり、リアルタイムの遅延情報を取り入れたりといった工夫もほしい` (verbatim build request; defines the whole product: route registration + selection, position-aware catchable-train prediction from timetable, walking-speed learning, live delay info)

## Station / bus-stop search overhaul (edit 2026-11-10)
- User report (verbatim in the edit brief): 「駅やバス停の検索性が悪すぎる。」
- Diagnosis (tested 2026-11-10): the old `searchPlaces` was a single unbounded Nominatim free-text query, limit 6. Measured failures: `新宿駅` → administrative areas in China/Brazil/Mongolia, then station entrances （出入口） instead of the station; `金閣寺前` (Kyoto City Bus stop) → a traffic signal of the same name; bus stops classified as 住所 (highway catch-all); no Japan bounding, no name-match filtering, no dedupe beyond exact coordinates.
- Fix: `searchPlaces` now fans out in parallel and merges with name scoring (exact > prefix > contains > bigram-Dice ≥ 0.34 for fuzzy sources), dedupe by name + ~100 m, stations/bus stops ranked first, optional `nearLat/nearLng` bias (the picker passes the chained previous spot's coordinates from RouteEditor). If no bus stop surfaces and the query lacks バス停, one extra Nominatim pass with ` バス停` appended runs (its tokenizer only then restricts to bus_stop features). Station candidates carry a `line`, and RouteEditor auto-fills an empty 路線名 when a station candidate is picked.
- Verified via the built action: `新宿駅` → 新宿駅 grouped per operator with line names (was: foreign cities); `出町柳` → 京阪本線/叡山電鉄本線 stations, then 出町柳駅前 bus stops; `四条烏丸` → the actual intersection bus stops; `金閣寺前` → 金閣寺道 bus stop (the real stop serving 金閣寺; the exact-name stop is absent from OSM); `京都市北区金閣寺町1` / `東京都新宿区西新宿1-1-1` → exact 番地-level addresses (GSI).

## Chained spots in the route editor (edit 2026-11-10)
- User request (verbatim in the edit brief): in route registration, only the first spot should need manual entry; from the second spot on, the previous spot must automatically become the departure point. Previously the first segment added after the origin was NOT pre-filled (the origin's spot lives in `place`, but `add()` read the previous segment's `toPlace`), and editing a spot did not propagate to the adjoining segment.
- Fix (client-only, `RouteEditor.tsx`): segments are one continuous chain. `endPlaceOf()` treats the origin's spot as its end; `add()` pre-fills the new segment's start from it; place edits are chain-aware (`setStartPlace`/`setEndPlace` rewrite the neighboring segment's matching end); reorder/removal re-links via `rechain()`. No schema or server change.

## Chained start spots are display-only (edit 2026-11-10)
- User request (verbatim in the edit brief): since the departure spot is now auto-filled (chained), the place-registration fields for the second and later spots are unnecessary.
- Change (client-only, `RouteEditor.tsx`): walk segments no longer render a full PlacePicker for 出発地 and ride segments none for 乗車駅 — the chained start spot is shown read-only (name, address, 地点登録済み badge) with a note that it comes from the previous spot and is changed by editing the previous segment's end. Full pickers remain only where a new spot is actually registered: the origin and each segment's end （到着地 / 降車駅）. Because a ride segment's boarding station can no longer be picked directly, picking a station candidate as the previous segment's end now also fills the following ride segment's empty 路線名 (as does adding a ride segment after a station end spot). No schema or server change.

## Line-diagram station picker + automatic timetables (edit 2026-11-10)
- User request (verbatim in the edit brief): for train/bus ride segments the alighting station must be picked from the line diagram (per line, per direction — up/down), not general place search; departure times must not be entered by the user at registration — they should be fetched automatically from the route, because the app is launched from any position at any time on the route and must do the transfer time arithmetic itself.
- Line diagram: new `getLineStations` action wraps HeartRails `getStations&line=<line>` (tested: `京阪本線` returns every station with x/y, prefecture, prev/next; order rebuilt from the prev/next chain). New `getStationLines` action wraps `getStations&name=<station>` for the lines serving the chained boarding station (one-tap line chips). Client `LineStationPicker`: direction tabs are the two terminals （○○方面）, the list shows only stations reachable from the boarding station in that direction, in travel order, with 駅目 counts and the boarding station pinned on top. Lines absent from HeartRails (most bus routes) honestly fall back to the general PlacePicker with a note.
- Bus limitation (explicit, disclosed in the editor; PARTIALLY SUPERSEDED by the GTFS section below): the line-diagram picker and the ekitan automatic timetable cover RAIL lines only. No tested source offers a server-rendered bus route diagram: HeartRails is rail-only, and ekitan's bus section (bus.ekitan.com) is a separate legacy service without the clean area→line→stop structure the rail side has (checked 2026-11-10: the route-bus company pages carry no stop-list links). For bus segments the alighting stop is therefore registered via the general place search, and automatic timetable fetching is attempted only via the generic operator-page fallback, which may fail; the RouteEditor ride-section note and the LineStationPicker fallback message both state this where the user meets it. → Update (2026-11-10, GTFS edit): bus operators published in the MLIT GTFS Data Repository now DO get a line-diagram picker and automatic timetables from their GTFS-JP feeds; the fallback above remains only for operators the repository does not cover (incl. 京都市バス — ODPT token required).
- Automatic timetables: registration no longer asks for any departure times (the four textareas and the interval generator were removed from RouteEditor; previously stored timetables on older routes are preserved untouched and used as-is). New `timetable_cache` table (migration 0004; unique key line+station+toward) and `fetchTimetable` action. The board auto-fetches any ride segment that has neither a stored nor a cached timetable when the route is opened, shows per-segment status （自動取得済み + source link + age / 取得中 / 取得できませんでした + 再試行）, and merges cached times into predictions via `applyTimetables()` in predict.ts (keyed by line + station-core + toward-core, 駅 suffix stripped).

### Ekitan （駅探） timetable source (fetchTimetable primary; tested 2026-11-10)
- Why ekitan: its station timetable pages are fully server-rendered HTML, so a plain server `fetch` gets the whole day's departures as text. NAVITIME answers 403 (CloudFront) to server fetches and ジョルダン is JavaScript-rendered; `ctx.tool.web_search` essentially never returns ekitan timetable pages, so the station entry point is resolved WITHOUT search (below).
- URL shapes (all verified live): station page `https://ekitan.com/timetable/railway/station/<id>` (per line: direction links with 「○○方面」 anchor text); line page `https://ekitan.com/timetable/railway/line/<id>` (lists every station page on the line); regional index `https://ekitan.com/timetable/railway/area/<0-9>` （関東0/関西1/東海2/北海道3/東北4/北陸5/甲信越6/中国7/四国8/九州・沖縄9; lists every line in the region); direction timetable `https://ekitan.com/timetable/railway/line-station/<code>/d1|d2`.
- Day types: a `?dt=YYYYMMDD` query picks the service day — a Tuesday renders the weekday timetable, a Saturday the holiday one (verified: 出町柳 京阪本線 weekday 203 departures incl. commuter expresses vs Saturday 183 without; `?dw=` is ignored by the site).
- Resolution (deterministic): boarding station's prefecture from the HeartRails line diagram → regional index → line link (name match, JR-/線-normalized) → line page → boarding station page → that line's direction links. Direction is chosen by matching the 方面 label's station names against the HeartRails station order on the alighting side (fallbacks: label names the alighting station; a train page whose stop list runs boarding → alighting). Search-result URLs (station page / train page `sf=`=station id, `SFF=`=line-station code / line page) remain as backup paths. Extraction is a deterministic regex over the text under すべての時刻 — no model inference. Fallback if ekitan fails: the older web-search + `ctx.inference` extraction over other timetable pages; if that also fails, an honest error and nothing is fabricated.
- Verified via the built action: 京阪本線 出町柳→三条 (weekday 203 / holiday 183 departures, first 5:00/5:20/5:36/5:52/5:58 — matches the ekitan page), 京阪本線 三条→出町柳 (opposite direction d2 chosen correctly), JR山手線 新宿→池袋 (title ＪＲ山手線 池袋・田端・上野方面， ~370 weekday departures from 4:43).

### GTFSデータリポジトリ (MLIT) — ADOPTED for bus line diagrams + bus timetables
- Public API v2, no API key: base `https://api.gtfs-data.jp/v2`, docs `http://docs.gtfs-data.jp/api.v2.html` (OpenAPI; endpoints below confirmed from the docs + the site's own JS bundle + live calls).
- Catalog: `GET /v2/feeds` (all 610 feeds, ~570 KB gzipped; org/feed names, per-feed license e.g. `CC BY 4.0` / `CC BY 2.1 JP` / `CC0 1.0`, `real_time` URLs) and `GET /v2/feeds?org_name=<前方一致>`; geographic discovery: `GET /v2/files?extent=<minLng,miny,maxLng,maxy>` returns the feeds whose stops fall in the box (tested: Nishinomiya box → 西宮市/神戸市 feeds; Kyoto box → only 神姫観光 Limon Bus).
- Download: `GET /v2/organizations/<org_id>/feeds/<feed_id>/files/feed.zip?rid=current` → 302 to an S3 presigned URL; `fetch` follows it (curl -L stalled through this sandbox's proxy; Bun fetch completed: さくらやまなみバス feed 470,733 bytes in ~3 s). Per-feed page for attribution links: `feed_page_url` = `https://gtfs-data.jp/search?target_feed=<org>*<feed>`.
- Coverage finding (full-catalog scan 2026-11-10): NO feeds for 京都府 (pref 26) at all, and none for 京都市交通局 / 京阪バス / 阪急バス / 奈良交通. The repository skews to municipal/community operators (610 feeds; 兵庫 38, 三重 40, 高知 52…). 西日本JRバス appears only with the discontinued 名金線 (abolished 2022). So the repository closes the bus gap for covered operators only; Kyoto's major bus operators remain ODPT-only (below).
- ZIP handling: the runtime has `DecompressionStream("deflate-raw")` (verified in Bun), so actions.ts carries a hand-rolled central-directory ZIP reader — no new dependency. GTFS-JP parse: agency/routes/stops/trips/stop_times/calendar. Day-type split maps calendar services onto the app's two buckets (Mon–Fri ⇒ 平日, Sat/Sun ⇒ 土休日; calendar_dates exceptions not modeled). Guards: ZIP ≤ 30 MB, stop_times ≤ 2M rows, materialized departure rows ≤ 40k — oversized feeds fail honestly.
- Caching: a feed is downloaded/parsed once and materialized into `gtfs_feed_cache` (metadata + route list), `gtfs_line_cache` (per route+direction ordered stops = the bus line diagram; representative trip = most stops) and `gtfs_departures` (per route+direction+stop minute lists) — migration 0005. TTL 7 days; board opens never re-download.
- Integration: `searchBusFeeds` (extent around the chained boarding stop + operator/feed-name match), `getBusFeedRoutes`, `getBusRouteStops` feed the new `BusGtfsPicker` inside LineStationPicker, rendered wherever the rail diagram is unavailable (HeartRails miss or no line typed yet); picking a stop sets the segment line to the GTFS route name. `fetchTimetable` tries the GTFS cache first (line name match + boarding/alighting both on one cached diagram, in order), then ekitan, then the generic fallback — so bus segments picked from the diagram get automatic timetables through the existing timetable_cache/applyTimetables path, with sourceTitle `GTFSデータ（<事業者>・<フィード名>／GTFSデータリポジトリ）` and the feed page as sourceUrl.
- Attribution: repository licenses are per-feed CC variants requiring provider credit; the picker shows `データ提供: <organization>（<feed name>）／<license>／GTFSデータリポジトリ` + 出典ページ link under the stop list, and the board shows the same credit via the timetable source title/link.
- End-to-end verified via the built actions (2026-11-10): 西宮市 さくらやまなみバス — extent + name search both return the feed; route K0 （金仙寺系統） diagrams for both directions return ordered stops with coordinates （山口営業所前⇔阪急西宮北口駅, 19 stops); `fetchTimetable` 田尻橋→山口営業所前 returns weekday [7:16, 7:39, 8:28] exactly matching the feed's stop_times, reverse direction 山口営業所前→阪急西宮北口 returns [5:25, 7:50]; rail regression 京阪本線 出町柳→三条 still returns ekitan's 203 weekday departures.

### ODPT （公共交通オープンデータセンター) — token-gated; informational note only, NOT integrated
- API test: `GET https://api.odpt.org/api/v4/odpt:Operator` without a key → HTTP 403, body `Require acl:consumerKey.` A free developer registration + individualized access token is required; no token is configured for this app and there is no approved in-app secret-entry path, so no ODPT integration was built (no fake wiring).
- 京都市営バス GTFS lives here: CKAN catalog dataset `kyoto_municipal_transportation_kyoto_city_bus_gtfs` (resource 京都市営バス-20261104), whose download URL is `https://api.odpt.org/api/v4/files/odpt/KyotoMunicipalTransportation/Kyoto_City_Bus_GTFS.zip?date=20261104&acl:consumerKey=[アクセストークン/YOUR_ACCESS_TOKEN]` — token placeholder in the official link itself. License: 公共交通オープンデータ基本ライセンス + 特定利用条件. 京都市バスのデータセット page on data.city.kyoto.lg.jp (dataset 00656) points at the same ODPT dataset.
- What a token would unlock: 京都市バス （系統・停留所・時刻表 GTFS), 京都バス, and ODPT's rail+bus coverage incl. GTFS-RT for some operators. The app now states this honestly in the board's データについて section (free token required, not configured, hence those operators are out of scope for auto-fetch) — no credential field was added.

### GTFS-RT — reachable without a key for some repository feeds; documented future work
- 54 of the 610 repository feeds carry `real_time` URLs (trip_update / vehicle_position / alert), many on the public host `realtime.gtfs.info`. Verified reachable from the server: `GET https://realtime.gtfs.info/takeyakotsu/trip_update.pb` → HTTP 200, `application/x-protobuf`, 994 bytes, no key.
- Not wired in this edit: the prediction model keys on departure minutes per segment, not GTFS trip_ids, so consuming TripUpdate delays honestly needs a trip-level join (timetable cache would have to retain trip ids per departure) plus a protobuf decoder. Recorded here as the concrete next step; today's delay path (official-line-page search + manual override) is unchanged. 京都市バス provides no GTFS-RT at all （京都バス株式会社 only, via ODPT/NEC Nexa).

### OpenTripPlanner — not adopted
- OTP is a routing engine (server process + graph build); this app does fixed user-registered routes with per-second catchability math in predict.ts, not open-ended routing. No fit; noted for completeness since the screenshot listed it.

## Direction unification (edit)
- Schema: migration 0003 adds place fields + `to_lat/to_lng` + `departures_return` to `segments`, and `direction`/`direction_source` to `app_settings`. One route is bidirectional: places/stations/walk times/ride times are shared; only ride timetables may differ per direction (return timetable optional, falls back to the outbound one).
- Client: `reversedRoute()` builds the return view (segment ids preserved, so pace learning applies both ways); `detectDirection()` auto-detects from GPS — movement along the route first, then proximity to either end (within 800 m, and only when within 3 km of the route polyline). Detection runs on the board's continuous GPS watch and persists via `setDirection`. A small correction link （行きに切り替え/帰りに切り替え） is the only manual control; a manual correction is stored with source `manual` and auto-detection does not override it (「自動判定に戻す」 releases it).

## Renamed-station aliases — 阪急梅田駅 not found as a station (edit 2026-11-10)
- User report (verbatim in the edit brief): 「阪急梅田駅が駅として出てこないよ、バス停ならあるけど。」
- Diagnosis (all verified live 2026-11-10): the station was renamed 阪急梅田 → 大阪梅田 in 2019, and every source only carries the current name. HeartRails `getStations&name=阪急梅田` → `{"error":"Station '阪急梅田' not found."}` (name=大阪梅田 returns the Hankyu 3 lines + 阪神本線 rows). Photon DID return the 大阪梅田 station node for q=阪急梅田, but `namePlausible` rejected it: bigram Dice（阪急梅田 vs 大阪梅田）= 0.333 < 0.34 threshold. Nominatim for 阪急梅田駅 returns only the `highway/bus_stop` 阪急梅田駅 — hence exactly the reported symptom (bus stop only, no station).
- Fix (server-only, `actions.ts`):
  - `STATION_NAME_ALIASES` + `stationNameVariants()`: old/operator-prefixed name cores → current official names. Entries verified live against HeartRails the same way （近鉄難波・阪神難波 → error, 大阪難波 → 近鉄奈良線/阪神なんば線； 河原町 → only Sendai/Kumamoto stations, 京都河原町 → 阪急京都本線； 三宮 → 神戸三宮 for the Hankyu/Hanshin station): 阪急梅田・阪神梅田 → 大阪梅田， 近鉄難波・阪神難波 → 大阪難波， 河原町 → 京都河原町， 三宮 → 神戸三宮.
  - `searchHeartRails` and the station Photon pass in `searchPlaces` query every variant and score candidates against the variant that produced them (alias hit = exact match). `getStationLines` resolves lines through variants too.
  - `namePlausible` gained a renamed-station shape rule: shared name tail ≥2 chars, ≤2 leftover chars per side, AND zero common prefix (the prefix condition keeps 金閣寺前 vs 金昌寺前・金泉寺前 — shared head 金 + tail 寺前， different stops — rejected; regression-tested).

## Midosuji fetch failure + both-directions merge + direction-pick fix (edit 2026-11-10)
- User report (verbatim in the edit brief): 「なんか御堂筋なんばの時刻表の取得が上手く行ってないよ。」Diagnosed live against ekitan; THREE distinct bugs, all in the ekitan path:
  1. **Operator line names**: ekitan calls the line 大阪メトロ御堂筋線， the station DB (HeartRails) and the stored route call it 大阪御堂筋線. `lineNameMatch`'s substring checks fail on the infix メトロ ("大阪御堂筋" is not a substring of "大阪メトロ御堂筋"), so no ekitan path ever matched the line and fetchTimetable returned 「駅探で『なんば駅』の『大阪御堂筋線』時刻表を見つけられませんでした」. Fix: `lineNameMatch` now also compares operator-stripped cores （大阪メトロ/東京メトロ/都営/市営/営団 prefixes and メトロ/地下鉄/市営/都営 infixes and a leading city name removed from both sides; exact equality, min length 2).
  2. **Both directions merged**: an ekitan direction page embeds BOTH directions' timetables as `<div class="search-result-body" data-direction="1|2">` blocks (the unselected one is class-`hidden`), in the same order on d1 and d2 pages. `parseEkitanTimes` stripped the whole page text, merging both directions for every mid-line station (verified: なんば御堂筋 d1 = 316 northbound + 313 southbound → 561 merged; 三日市町 100 + 72 → 167 merged — the user's cached rows carried exactly these merged counts). Terminus stations have one block, which is why earlier spot checks （出町柳 203, 大阪梅田 251) passed. Fix: new `ekitanDirectionSlice()` isolates the requested direction's block in the raw HTML (by data-direction number from the /dN URL, else the non-hidden block, else the first), and parsing additionally stops at a second すべての時刻 block.
  3. **Direction-pick train fallback matched the wrong direction**: `pickEkitanDirection`'s last-resort train-page check compared FIRST occurrences in the whole page text — but the train page header names the boarding station before the stop list, so a wrong-direction train that passes the alighting station BEFORE the boarding one still "matched" （梅田→なんば picked d1 江坂方面： header 梅田 idx 629 < なんば idx 805 even though the stop order is なんば→梅田）. The fallback also read the first train link of the whole page (direction 1's block) for both candidates. Fix: the train link is taken from the candidate's own direction block (`ekitanDirectionSlice`), and the check compares boarding/alighting positions in the extracted stop sequence ("HH:MM発 <駅>" entries + terminus "HH:MM着 <駅>"), verified live: northbound train seq なんば pos 4 < 梅田 pos 8 (reject), southbound 梅田 pos 6 < なんば pos 10 (accept). Station matching in the direction pick / line-page anchors / station-page titles is now also prefix-tolerant (`stationCoreLooseEq`: 梅田 vs 大阪梅田， 難波 vs 大阪難波） and direction labels strip parentheticals （なかもず（大阪メトロ）方面）.

## Connection-search day-boundary bug (found by audit, fixed 2026-11-10)
- The audit's content review caught the board computing a 505-minute wait at なんば (arrive 20:42, walk 10 min, then "翌5:10発") despite the fixed Midosuji timetable being correctly cached. Root cause is in `buildChain` (predict.ts), pre-existing: for rides after the first, departures were scanned per-departure over day offsets [0, +1440] and the FIRST hit taken — for an early-morning departure that has already left (e.g. 5:10 at 20:52), its tomorrow instance always "matches", so the chain jumped to tomorrow's first train whenever the connecting line's first departure of the day had passed. Single-ride routes were unaffected (the first ride's candidates were filtered correctly), which is why earlier end-to-end checks passed. Fix: pick the earliest catchable departure TODAY; only when none remains, continue on tomorrow's first departure. Verified by simulation with the real lists at 20:11 JST: 南海 20:27発 → 難波 20:42着 → 御堂筋 20:57発 (12分待ち) instead of 翌5:10.

## Scenario comparison on the board (edit 2026-11-10)
- User request (verbatim in the edit brief): the board must not show "the timetable" but simulate traversing the registered route from now — and compare choices, e.g. Hankyu Rokko → (local, transfer to limited express en route) → Osaka-Umeda → Midosuji → Namba → Nankai Koya Line, where the fastest pattern can strand you at the final Nankai transfer; staying on the local can be better overall. "乗り換えて最短で帰る場合と乗り換えない場合でその後の駅で乗れる電車にどう違いが出てくるかを見たい。"
- Implementation (`computeScenarios` in predict.ts + シナリオ比較 section in App.tsx): the baseline scenario is the fastest full traversal (earliest catchable train at every boarding point, delay/walk/pace-aware, same engine as the hero). Each variant passes up ONE departure at ONE boarding point (the departure the baseline catches there is removed from that segment's list and the whole downstream chain is re-simulated with the unchanged engine), so every scenario shows, per station, the train caught (発/着）, the transfer wait at that station, total transfer wait, and the final arrival — with per-leg differences vs the fastest highlighted （最短より+N分） and arrival deltas （到着 +N分 / 到着は最短と同じ）. Tapping a scenario card promotes it into the hero board. This makes the user's phenomenon directly visible on their real route: an earlier arrival at なんば that misses the same 南海 train shows up as a long 難波 wait with no arrival gain.
- Honest modeling limit (unchanged data model): a choice made INSIDE one registered ride segment (e.g. alighting mid-segment to change from a local to a limited express on the same line, 六甲→梅田 as a single segment) cannot be split into scenarios, because the auto-fetched timetable stores departure minutes only — no per-train type or arrival times. The comparison covers every choice at a registered boarding point (which includes 六甲で1本見送る and each transfer station). Splitting mid-segment express transfers would require per-train data (ekitan train pages per departure) — recorded as future work, not faked.

## Long-term data behavior
- **Refresh policy**: line status is cached per line name in `line_status`; `refreshLineStatus` re-searches on user tap and on route open when cache is older than 10 minutes (client-triggered). Timetable/routes/walk-logs are user-owned and change only via explicit user actions. No scheduled cron: delay data is only meaningful at open/tap time.
- **Growth**: routes bounded by user entry; walk_logs grows one row per recorded walk segment (kept, used for learning averages; displayed recent-first, capped display at 50).
- **Ordering**: routes by created order with an `is_active` selection; departures sorted ascending within a day-part; walk logs newest first.
- **Time semantics**: all times are JST wall-clock minutes-of-day for timetables; walk log timestamps are instants rendered in the viewer's local timezone (user is in JST). Countdowns computed from the device clock each second against Asia/Tokyo time-of-day.
